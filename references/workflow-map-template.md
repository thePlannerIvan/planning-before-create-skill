# Workflow Map 模板

Grill 完成后使用。本 Map 是实现前最关键的用户确认面，不是工程字段清单。

## 精简 Workflow Map

```markdown
# [Skill Name] Workflow Map

## 目的与总体方法
[这个 Skill 稳定完成什么；从输入到结果的大致路径。]

## 触发与边界
- 应该触发于：
- 不应该触发于：
- 与相邻 Skill 的关系：

## 工作流

### Stage 1：[名称]
- 流程位置：
- 主要结果：
- 输入及其作用：
- 判断框架：
- 明确不做：
- 模型 / 工具分工：
- 必要的人类决定：无 / [用户不可替代的决定]
- 产物：
- 完成标准：

### Stage 2：[名称]
[同上]

### 按需增加的设计
只在真实存在时增加，不要给每个 Stage 机械填写：

- 脚本负责的确定性动作；
- 需要跨阶段或跨会话持久的状态；
- 机器交接的消费者与失败后果；
- 用户决定所需的展示、默认与反馈去向；
- Validator 能证明和不能证明的内容；
- 已有证据的 Gotchas。

## 分支
- [条件] → [路线]

## 人机介入点
| 决定 | 为什么必须由人做 | 时机 | 最少展示信息 | 不应展示 | 默认行为 | 反馈去向 |
|---|---|---|---|---|---|---|

## 资源
### references/
- [文件]：[只在什么判断中读取]

### scripts/
- [文件]：[减少什么机械负担]

### contracts/
- [文件]：[由哪个机器消费者使用；没有则不创建]

### assets/
- [文件]：[如何进入输出或审阅]

## 验证计划
- 工程检查：
- 语义样例：
- 人工 Review：
- 接口集成：
- failure mode 扫描（六种，见 `failure-modes.md`）：

## 持续迭代与减法
- 运行后自检：
- Gotcha 候选保存位置：无 / [已经用户确认的唯一长期位置]
- 周期优化触发信号：
- 本次需要删除或归档：
```

## 给用户的确认话术

```text
请重点检查：
1. 每个 Stage 的核心任务和顺序是否正确？
2. 模型需要的判断框架是否完整？
3. 脚本、持久状态和 Contract 是否都有真实需要？
4. 哪些人工介入真的需要你做决定？
5. 运行后自检和 Gotcha 积累方式是否可接受？

在这张 Map 被确认或修正前，我不会开始实现。
```

## 完成标准

- 用户能快速把握全景；
- 每个 Stage 围绕一个主要结果，相关认知动作不被人为拆散；
- 每个脚本都减少真实机械负担；
- 每个 Contract 都有明确机器消费者；
- 每个人工介入都对应模型无法替代的决定；
- 语义完成与机器检查边界分开；
- 已列出需要删除或归档的旧内容；
- 用户已经确认或修正。
