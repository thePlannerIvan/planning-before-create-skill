# Skill 的架构：模块、接口、缝

划分 module、写模块与边界说明时读取本文件。它管的是**目标 Skill 本身的结构**，不是它的内容质量。

## 为什么必须写进 Skill

设计阶段讨论出来的模块划分、边界和上下游配合，如果不落到目标 Skill 的文件里，下一个改它的人（或模型）**不在场**：他会看到一堆文件和规则，看不出哪块负责什么、哪条缝归谁、动了会牵连谁。于是两种典型后果：

- **重复实现**：同一件事两处各写一份，改一处漏一处；
- **隐形步骤**：流程里必经的一步既没有被写成可见的 Stage，也没有任何东西检查它是否发生——见 `failure-modes.md` 的「隐形步骤」。

所以：**模块的作用、边界和用法要写在 Skill 里**，写在改它的人会读到的地方。

## 一套词汇（用外部 Skill `codebase-design` 的词，不要漂成「组件／服务／API／边界」）

| 词 | 在 Skill 里指什么 |
|---|---|
| **module** | 一个能被独立说明职责的单位：一个 Stage 文档、一个脚本、一份 Contract、一个 Reference、一组 Asset、frontmatter 的触发面。**module 与规模无关**——一个函数和一个 Stage 都可以是 module。 |
| **interface** | 别人（模型或另一个 module）与它打交道的那一面：脚本的命令行与输入输出、Contract 的字段、Stage 文档的「输入及其作用／产物／完成标准」、`SKILL.md` 里指向它的那一行。 |
| **depth** | 实现藏在接口后面的比例。**深 module**：接口小、后面的判断多（一个 Stage 说清一件事，模型据此做大量判断）。**浅 module**：接口几乎和实现一样复杂（一份 Reference 只是把文件列了一遍，模型读完还得去别处拼）。 |
| **seam** | 两个 module 之间的接缝——谁交出什么、谁消费什么。 |
| **adapter** | 缝上的翻译层：把上游的形状翻成下游认识的样子。 |
| **leverage** | 修一处、影响一片的能力。 |
| **locality** | 改一个行为只需要看一个地方。 |

两条硬判据：

- **删除测试**：删掉这个 module，复杂度是**被集中**了，还是只是**搬家**了？「被集中」才是要的信号——它说明这个 module 本来就是多余的中间层。
- **一个 adapter 是假缝，两个才是真的**：只有一处做翻译时，先怀疑它是多余的中间层；两处以上各自实现同样的翻译，那条缝就是真的，把翻译收到一处。

## 每个 System 路线目标 Skill 必须有两个文件

放在目标 Skill 里，并且 `SKILL.md` 要有一行指向它们。

### 一、`references/architecture.md` —— 模块与边界

按下面的顺序写，**不要写成文件清单**：

1. **目的与全景**：这个 Skill 稳定完成什么，从输入到结果大致怎么走。
2. **模块表**：每个 module 一行——它是什么、**拥有什么**（谁是这件事的唯一主人）、**接口**是什么（别人怎么用它）、**不做什么**。
3. **缝与适配器**：跨 module／跨 Skill 的接缝，各自谁交出什么、谁消费什么；有 adapter 的写清它在哪、翻什么、谁读它。
4. **与相邻 Skill 的关系**：上游交什么、下游要什么、什么**不**归本 Skill 管。
5. **同一件事的两个真相源要单独标出**：两个库、两份声明、两个审阅面——它们**为什么**分开，以及谁读谁、谁不读谁。
6. **退役**：哪些旧机制已经不在运行路径里，为什么删除或封存。

写「动的后果」比写「有什么文件」重要：读它的人要能回答**「我要改 X，应该动哪里、会牵连什么」**。

### 二、gotcha 与升级记录 —— 候选与升级分开

| 文件 | 装什么 |
|---|---|
| `GOTCHAS.md`（Skill 根） | **候选**：有证据的、会稳定导致错误的具体行为（记录模板见 `continuous-iteration.md`）。 |
| `references/maintenance-history.md` | **升级**：一次改动做了什么、为什么、影响了哪些 module、删了什么。 |

**分开放的理由**：候选会很多、会合并、会失效，需要能被批量审阅；升级是已决定的事实，需要能被回溯。混在一起，两者的生命周期会互相污染。

## 自查：这份 Skill 清晰吗

改完目标 Skill，用下面的**清晰度四问**自查。**任一条答不上来，缺的是 writing，不是功能。**

```text
□ 一个没参与设计的人，只看 SKILL.md，能不能说出整条流程有哪几步、每步产出什么、怎么一眼看出这一步没做完？
□ 每个 module 的作用、接口和「不做什么」，能不能在 Skill 里读到（而不是只在设计对话里）？
□ 跨 module／跨 Skill 的缝，能不能读到「谁交出什么、谁消费什么」？
□ 一条新 gotcha 该记在哪、一次优化该动哪个 module，能不能读到？
```

**`SKILL.md` 的流程表是模块表的摘要，不是第二份完成标准。** 写到「一眼能不能看出这一步没做完」为止——这一步做什么、主要产物是什么（落什么盘）、怎么一眼看出没做完。**完整的完成标准只住在那个 module 自己的文档里。** 两处都写全，就又造了一个真相源。

两条分支的步序不同时，**先看它们的完成标准是否也不同**。不同就分开写，别为了方便塞成一张表加一列——合表会把两边的判据搅在一起。

再加一遍删除测试的落地检查：

```text
□ 有没有 module 删掉之后复杂度只是搬家？→ 它本来就不该存在
□ 有没有同一件事被写了两遍？→ 合成一处，其余留指针
□ 有没有必经步骤没被写成可见的 Stage，也没有任何东西检查它？→ 隐形步骤
□ 有没有 Contract／Script／Reference 在 Active 路径上没有消费者？
```
