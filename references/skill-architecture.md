# Skill 的系统架构：深模块、接口与接缝

划分模块、设计工具接口与编写目标 Skill 的架构说明时，读取本文件。它管的是**目标 Skill 本身的系统结构与工程质量**。

## 为什么必须把架构写进 Skill

设计阶段对模块划分、工具接口、业务边界的取舍，如果不落到目标 Skill 的代码与文档里，下一个修改它的人（或模型）**不在场**：
他会看到一堆脚本和 Prompt 规则，看不出哪块负责什么死逻辑、动了会牵连哪个下游。后果就是：
- **重复实现**：同一段数据处理或正则在 Prompt 和脚本里各写一遍，产生两份真相源；
- **浅模块泛滥**：为了划分而划分，写了一堆互相套娃的微型脚本，反而增加了心智负担。

因此：**模块的主人、工具接口契约与明确的“不做什么”，必须沉淀在目标 Skill 中。**

## 核心概念词库（高杠杆架构词）

直接借用软件设计与深模块（Deep Module）的核心杠杆词，精准界定概念：

| 词 | 在 Skill 系统中指什么 |
|---|---|
| **module** | 一个能被独立说明职责的高内聚单元：一个确定性工具脚本（Script）、一份专业 Reference、一段场景 Playbook、或 frontmatter 的触发面。**module 与行数无关，与内聚性有关**。 |
| **interface** | 外部（模型、用户或其他脚本）与它交互的显式通道：脚本的 CLI 参数、标准输入输出与退出码；Playbook 的触发条件与产出物契约。 |
| **depth** | **深模块 (Deep Module)**：接口极小，背后解决的问题极深极重。例如：一个脚本把脏数据清洗、重构和校验全部搞定，对外只暴露 `--input` 和 `--output`；或一个核心概念三句话讲透领域根本机制。<br>**浅模块 (Shallow Module)**：接口几乎和实现一样复杂（反模式）。例如：一个脚本只是把一段简单的 bash 命令包了一层皮，模型调用它还得传一堆繁琐参数。 |
| **seam** | 接缝：两个 module 之间、或 Skill 与外部环境打交道的交接面——谁提供数据、谁消费数据。 |
| **adapter** | 接缝上的格式翻译层：把上游产物转换为下游工具认识的标准格式。 |
| **leverage** | **杠杆率**：修一处、影响一片的能力。工具封装越深，杠杆率越高。 |
| **locality** | **局部性**：修改一个具体业务行为只需要动一个文件，不用满天星式地改到处引用的 Prompt。 |

### 两条硬核架构判据：
1. **删除测试 (Deletion Test)**：删掉这个 module（脚本或文档），复杂度是**被真正消除了**，还是只是**搬家了**？
   - 如果删掉它之后，复杂度并没有消失，只是逼着模型在 Prompt 里重写一遍临时代码，说明它是**真工具**，必须保留；
   - 如果删掉它之后，系统反而更清爽，没有任何能力缺失，说明它是**多余的中间层**，必须坚决删除。
2. **一个 adapter 是假缝，两个才是真缝**：如果只有一处做格式转换，直接由调用方消化，不要特意建一个适配器；当两个以上工具都要处理同一种异构数据时，才把转换逻辑提取为独立的转换工具。

## 每个 System 路线目标 Skill 必须沉淀的架构文档

目标 Skill 必须在 `references/architecture.md` 中写明系统骨架，并在 `SKILL.md` 中留有一行指针。

### `references/architecture.md` 书写规范（禁止写成简单文件清单）

按以下结构清晰陈述，重点写**职责所有权与调用的后果**：

1. **业务目标与 3+1 全景**：这个 Skill 稳定交付什么终局，输入到产出的宏观工作流。
2. **模块与工具表**：每个 module（重点是确定性脚本）一行：
   - **名称与定位**：它是做什么的；
   - **唯一责任人 (Ownership)**：谁是这项确定性工作的唯一主人（杜绝 Prompt 与脚本重复实现）；
   - **接口契约 (Interface)**：命令行参数、输入输出格式（纯数据/JSON/Markdown）、异常退出码；
   - **明确不做什么**：严禁它越界承担什么。
3. **接缝与数据流 (Seams)**：跨脚本、跨 Skill 的数据交接契约。
4. **真相源边界**：如果存在外部依赖库、规则配置或字典，标明唯一权威来源是谁，谁读谁、谁不读谁。
5. **退役记录 (Deprecation)**：哪些旧机制或脚本已被删除或废弃，为什么淘汰。

## 候选踩坑与升级记录（分开存放）

目标 Skill 的迭代记录遵循双轨制：
- `GOTCHAS.md`（Skill 根目录）：**候选池**。记录有真实运行证据的、容易误判或导致失败的具体行为（由运行后自检提取）。
- `references/maintenance-history.md`：**已决定的升级历史**。记录重大版本重构做了什么、为什么修改、删除了哪些冗余模块。

**分开放的理由**：Gotcha 是日常发现的待合并候选；升级历史是系统架构的事实演进。

## 架构自查：这份 Skill 清晰吗？

完成目标 Skill 设计后，用以下四问自查：

```text
□ 任何人只看 SKILL.md，能不能清楚说出：核心目标 (O)、验收判据 (KR)、有哪些工具 (Tools)、怎么组合调度 (Playbook)？
□ 每个确定性工具的作用、CLI 接口和「不做什么」，能不能在 architecture.md 里读到？
□ 工具是不是深模块？接口是否足够干净，内部是否消除了全部机械死逻辑？
□ 是否通过了删除测试？有没有为了看起来像系统而硬凑出来的无用脚本或空洞文档？
```
