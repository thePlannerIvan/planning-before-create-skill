# 模块与工具设计

多个模块、工具或跨系统交接需要明确职责时读取。先检查已有结构与实际调用方，再决定是否拆分。

## 模块边界

- **内聚与深度**：一个模块承担一个可解释的职责，以简单接口封装有价值的复杂工作。
- **接口与接缝**：明确谁提供输入、谁消费输出，以及失败时如何处理。格式转换是否独立取决于复杂度、复用和变更边界。
- **局部性**：同一个行为尽量只在一个位置维护。文档描述用途和调用方式，固定规则由实现或配置持有。
- **删除测试**：删掉模块后，工作是否消失，还是被迫在调用方重新实现？保留真正减少重复工作的模块。

## 工具的完成线

工具有真实使用者，输入输出可检验，失败能被调用方识别。用代表性样例和相关失败样例执行它；语法通过不代表功能正确。导入与命令执行都是运行测试，应在明确的测试环境中进行。

短任务可在上下文内保留状态；跨会话恢复、版本绑定或高成本交接需要时，保存最小可恢复状态。持久数据字段由实际消费方决定。

## 记录在哪里

简单 Skill 在入口说明即可。多个模块的职责、接口和依赖难以在入口清楚表达时，另建架构说明并加读取指针。复用已有架构文件，记录当前结构；历史决策放到项目已有的变更记录中。

本 Skill 的两个工具互不调用：`scaffold_skill.py` 只新建最小入口，`lint_skill.py` 只做静态检查。参数以各自 `--help` 为准；工具回归测试在 `tests/test_tools.py`。
