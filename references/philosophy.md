# 设计哲学

当以下任一信号出现时读取本文件（否则不需要）：
- 用户质疑某个设计取舍（"为什么这里要这样设计？"）；
- 模型发现两条规则或两个参考文件冲突；
- 需要向用户解释"为什么这么设计"而不是"做了什么"。

## Skill 是认知与行为系统

Skill 不只是说明书，也不只是流水线。它要让另一位模型理解：为什么做、如何判断、何时使用工具、什么时候找人、什么才算真正完成。

## 模型认知预算是稀缺资源

模型应把注意力用于理解、比较、抽象、创意、取舍和表达。机械搜索、转换、保存、恢复、格式检查和页面启动应尽量由脚本完成。任何新增文件、字段、回执和命令都必须证明它减少的负担大于增加的负担。

## 渐进披露不是信息压缩

先给模型整个 Skill 的简明全景，再在正确时间披露当前 Stage 的完整任务。当前任务不能被压缩成一串文件路径；Reference 只补充当前确实需要的知识。

## 状态需要持久化，思考不必全部结构化

跨阶段、跨会话、机器消费、版本绑定和回到来源所需的状态应该落盘。自然讨论、临时假设和不会被下游消费的思考不必强制写成 Contract。

## 工具各有边界

- Reference 是认知工具；
- Script 是机械执行工具；
- Asset 是生产工具；
- Contract 是机器交接工具；
- Human Checkpoint 是高价值决策工具。

工具不是越多越可靠。可靠性来自工具与失败模式匹配。

## 人机协作保护人的判断力

模型先完成资料能够支持的工作，人只在方向、价值、风险、承诺和最终内容等不可替代的节点介入。交互界面围绕当前决定组织信息，降低点击和噪音，但不替用户完成实质选择。

## 根本德性

好 Skill 的根本德性不是控制得最死，而是：

- 模型知道自己在做什么；
- 机械工作不挤占认知预算；
- 人只承担真正需要人的决定；
- 机器交接可靠；
- 系统能够通过删除保持清晰。
