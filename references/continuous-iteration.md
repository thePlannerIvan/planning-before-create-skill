# 运行后自检、Gotcha 积累与减法审计

创建或重构目标 Skill 时，完整读取本文件。设计阶段先让用户确认长期反馈保存位置；未确认时只做当次自检，不自行新建日志。

## 每次运行后都自检

目标 Skill 完成真实任务后，内部检查：

```text
□ 这次有哪个判断、工具调用或交付环节明显卡住？
□ 现有 Skill 是否给了错误引导，或没有改变模型默认行为？
□ 是否出现一个表面合理、但会稳定导致错误的具体 Gotcha？
□ 该发现是一次性过程、项目偏好，还是可迁移的 Skill 问题？
□ 现有候选中是否已有同义项？
```

没有新的可复用发现时，不创建文件、不追加空记录、不输出维护总结。

## Gotcha 候选的最小记录

只在设计阶段已确认的唯一长期位置中积累，优先使用已有 Project Memory、feedback 文件或稳定数据目录，不要在多个位置复制。每条只保留：

```text
- 现象：[实际发生了什么]
- 原因：[为什么现有 Skill 没有防住]
- 行为修正：[下次应怎样做]
- 证据：[哪次运行、产物或用户反馈支持]
- 状态：候选 / 已复现 / 已升级 / 已失效
```

追加前先合并同义候选。用户明确纠正或多次真实运行复现后，才把候选升级到 Active Skill；不因一次措辞修改就膨胀 Skill。

**候选与升级分开放**：`GOTCHAS.md`（目标 Skill 根，候选：会合并、会失效，需要批量审阅）与 `references/maintenance-history.md`（升级：已决定的事实，需要回溯）——文件定义与分开的理由见 `skill-architecture.md`。

**每条候选都要指出它属于哪个 module**（Stage、脚本、Contract、Reference 还是触发面）。优化时按 module 聚类——不按发生次数堆规则，也避免在错的层上修。

## 积累后的周期优化

出现任一信号时进行批量审阅：

- 多个已复现 Gotcha 指向同一根因；
- 新候选开始与现有规则重复或冲突；
- 某个失败已明显影响质量、风险或操作成本；
- 用户要求优化 Skill。

周期优化时：

1. 按根因聚类 Gotchas，不按发生次数堆叠规则；
2. **先定这条根因落在哪个 module**，再去改那一层——改错层会让问题换个地方复发；
3. 修复最低权威层：Trigger、Stage、Reference、Script、Interface 或 Eval；
4. 用原始失败与相邻案例做 old/new 对照；
5. 删除已被新设计替代的旧规则、重复候选和失效 Eval；
6. 保留尚未复现的候选，不提前写入 Active Skill；
7. **边界变了就同步改**目标 Skill 的 `references/architecture.md`，并把这次改动记进它的 `references/maintenance-history.md`。
8. **改一条口径时，先 grep 它在全 Skill 的出现处，一次性对齐。** 只改你手上这一处，下一个**新写的**文档就会把那句旧的当事实抄走——于是同一个 Skill 里出现两个互相打脸的说法，而且两边看起来都像现行规则。同一个事实只在**一个 owner 文档**里写全，别处只留指针；那个 owner 文档里的表述**尽量写成表格**（谁／什么时候／代价），表比句子更容易在下一次被逐格核对。

## Memory 不是日志

运行后只保留会改变未来行为的内容：

| 发现 | 去向 |
|---|---|
| 当前任务的一次性过程 | 不进入长期 Memory |
| 用户或项目稳定偏好 | Project/User Memory |
| 某一步偶发经验 | Step Memory Candidate |
| 连续复现的通用流程缺陷 | 对应 Stage、Reference、Script 或 Interface |
| 真正机器接口缺字段 | Contract、Producer、Consumer 与 Validator |
| 重复确定动作 | Script |
| 触发错误 | Frontmatter Description |
| 旧规则失效 | 删除或移出 Active |

不要因为某次改句就膨胀 Skill，也不要把完整运行日志称为 Memory。

## 升级必须同时做减法

重大升级结束前执行 Subtraction Audit：

```text
□ 哪些旧规则已被新设计替代？
□ 哪些 Contract 已没有机器消费者？
□ 哪些 Script 不再处于运行路径？
□ 哪些 Reference 没有清晰入口？
□ 哪些 Eval 仍在保护旧行为？
□ 哪些 Asset 或模板已经过期？
□ 哪些兼容层、别名和临时输出会误导模型？
□ 本次实际删除或归档了什么？
```

如果本次只增加、没有删除，必须说明为什么旧系统没有任何失效内容。不能用“保留以防万一”代替判断。

## 目标 Skill 的精简运行后规则

目标 Skill 默认保留内部自检；只在任务会长期复用且用户已确认保存位置时，加入持久积累规则：

```markdown
## 运行后迭代

1. 每次运行后做 Gotcha 自检；没有可复用发现时不留记录。
2. 一次性过程不写入长期 Memory。
3. 会改变同项目下次运行的偏好和约束写入 Project Memory。
4. 用户明确纠正或多次复现的通用问题才升级到 Skill。
5. 新规则落地时同步合并重复项并删除失效规则和资源。
```

简单、一次性或没有持续状态的 Skill 不必机械加入 Memory Audit 章节，但仍在当次运行结束时完成内部自检。

## 轻量反馈

只有当以下信号出现时才问用户（否则不问，不要每次运行都输出维护总结）：
1. 同一流程问题连续出现 2 次以上；
2. 用户主动表达偏好或不满；
3. 出现需要长期写入的候选，但设计阶段尚未确认保存位置或写入边界。

信号出现时用如下形式问：

```text
这次有两个可能影响未来运行的点：
1. [项目偏好]
2. [通用 Skill 问题]

需要把哪一项写入项目记忆或 Skill 改进候选？
```
