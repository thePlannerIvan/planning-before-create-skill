# 迭代与减法

用于规则冲突、内容膨胀、重构，或用户希望积累真实经验再集中升级的场景。

## 从证据到修改

先读实际输入、产出、错误或用户纠正，区分一次性情境与可复用问题。按根因选择修正：机械错误修工具，语义误判补具体判据或反例，策略问题调整场景指引，触发问题修改 description。

尚未决定的发现可放入项目现有候选池；只有确有记录需要时才建 `GOTCHAS.md`，写清现象、条件、证据与建议归属。没有新发现就不建文件。候选经确认安装后移出候选池，重要取舍记入已有维护记录；两者有不同状态，无需为每个 Skill 预建两份空文件。

集中升级前对齐修改范围，复用已给出的授权。用旧行为或旧产物作基线，先完成相关项目测试，再一次性更新 Skill。不能把一次运行中的临时处理直接变成通用规则。

## 减法检查

| 现象 | 检查与处理 |
|---|---|
| 看起来做完但结果不可用 | 用真实输入和交付判据验证，定位漏掉的关键动作 |
| 同一规则出现多处 | 留一个权威出处，其余用指针或删除 |
| 旧规则、文件或用例残留 | 搜索调用方及代码引用，确认用途后清理；文档没有提及不等于无人使用 |
| 流程比任务更复杂 | 保留从输入到交付的主路线和继续、返回条件，按场景加载细节，移除无实际消费方的文档与中间层 |
| 精简后只剩目标和工具名单 | 补回每步工作与完成依据、工具用途与触发时机、核心交付的操作路径；方法已拆出时用明确指针连接 |
| 泛泛要求没有改变行为 | 改成有用的判据，或删除 |
| 必要动作总被遗漏 | 明确触发条件与验证方式 |

搜索本次改动涉及的事实、文件和调用方，同步更新入口、参考资料、模板、用例及实际依赖方。范围以受影响行为为准；检查后确实没有冗余时可以只修问题。

## 设计演变与旧规则退役

用户确认新设计后，把当前有效行为写在负责该能力的模块中，说明适用范围、预期体验与可观察结果。跨 Skill 的公共能力由公共模块持有规则；调用方给出明确的读取指针。后续修改该能力前先读当前规则，再判断现有实现是否需要修正。

沿调用链检查旧说明、实现、模板、默认配置和验收用例，更新或删除与新设计相冲突的部分。既有代码和旧测试只能说明过去的行为，不能据此把用户已放弃的设计加回来。确需兼容的旧行为隔离到明确的旧项目入口，不作为新项目默认值。历史记录标明哪些设计已被替代，并指向当前规则；不让新旧方案并列成为执行依据。

例如，某审阅模块已确定“编辑自动保存，用户查看历史或恢复版本”，就应清理其调用方的“点击保存”要求及相反的测试；底层仍可有保存 API，但不据此增加用户保存按钮。这项交互约定归该审阅模块，通用 Skill 维护规则只要求完成设计替换与一致性检查。

对曾反复回归的问题，补能观察用户结果的用例，覆盖新行为以及旧行为不再出现。验证按实际风险与本轮约定安排；尚未执行的联合验证明确记录为待验证。

## 内容与结构的减法

减少字段时，先检查它承载的专业含义。重复表达同一判断的字段可以合并；支撑理由、证据边界等信息仍需有清楚的表达位置。

例如，方案主线可以简化为每页一句主张、下面两三条可展开的支撑判断。支撑可以并列或递进，不强套关系；“消费者分析／沟通问题／优化建议”只是栏目名，不能替代论证。省掉块角色、格式建议等字段后，仍须让下游理解本页主张如何成立。数量和形式服从实际任务，不把这个例子作为所有 Skill 的模板。

## 验证

局部修补验证受影响的行为；结构改动对照代表性任务的前后结果。报告实际删除、保留的理由与测试限制。真实使用后再观察新规则是否有效，未执行的未来验证不能写成已经通过。
