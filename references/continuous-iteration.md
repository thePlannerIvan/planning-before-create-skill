# 运行后自检、Gotcha 积累与减法审计

本文件指导目标 Skill 在真实运行后的持续进化机制。好的 Skill 不是一次性写死的，而是在真实使用中不断通过**积累反例、下沉确定性工具、做减法审计**而变得精悍。

---

## 1. 运行后静默自检

目标 Skill 完成真实任务后，在内部做自检（不向用户输出琐碎的维护汇报）：

```text
□ 这次有哪个关键判断、脚本调用或交付环节明显卡住？
□ 是否出现了一个模型表面觉得合理、但会导致业务错误的具体 Gotcha？
□ 现有 Skill 是否缺少了某个具象的反例（Negative Case）？
□ 这个死逻辑是否依然在让模型手写，而没有沉淀为脚本工具？
□ 该发现是一次性偶发噪音，还是具有可迁移性的通用规律？
```

没有新的、有证据的可复用发现时，**不留记录、不建文件、不输出总结**。

---

## 2. Gotcha 候选池与双轨制记录

只有在真实运行、测试或用户纠正中复现的非显然错误，才记录为 Gotcha。

### 双轨制文件管理（严禁混在一个文件里）：
- **`GOTCHAS.md`（Skill 根目录）—— 候选池**：
  - 装尚未合并的、可能失效或待观察的具体踩坑记录；
  - 格式极简：
    ```markdown
    - 现象：[实际发生了什么]
    - 根因：[为什么现有 Prompt/工具没有防住]
    - 应对修正：[下次应如何做]
    - 归属模块：[Tools 脚本 / Playbook 战术 / KR 反例 / Description 触发]
    - 证据：[哪次运行或用户纠正]
    ```
- **`references/maintenance-history.md` —— 已决定的升级历史**：
  - 装已经落地生效的重大版本迭代：修改了什么、为什么修改、删除了什么旧内容。

---

## 3. 升级时的治理路径（按层归因）

当多个 Gotchas 指向同一根因，或用户要求优化 Skill 时，按以下决策树进行升级：

1. **确定性错误 -> 下沉为脚本 (Tools)**：
   - 如果是格式错乱、数据遗漏、计算偏差或机械检验失败，**坚决写成确定性脚本**，不要试图在 Prompt 里用感叹号说服模型。
2. **语义误判 -> 补充具象反例 (KR / Negative Cases)**：
   - 如果是方向跑偏、理解肤浅、空洞说教，在 Key Results 里补入这个真实的翻车案例（Negative Case），用反例精准刹车。
3. **策略分支不清 -> 补充启发式战术 (Playbook)**：
   - 如果是特定输入场景下选错了路线，在 Playbook 里增加一条场景应对策略。
4. **触发误伤 -> 调整 Frontmatter Description**：
   - 优化触发词的专一性，收紧边界。

> **硬原则**：改动一个事实时，先全局 grep 搜索它在整个 Skill 里的所有出现处，**一次性对齐**。坚持单一真相源，绝不同时维护两个互相矛盾的说法。

---

## 4. 升级必须做减法 (Subtraction Audit)

任何一次优化或版本升级，必须同时进行减法审计：

```text
减法审计清单
□ 哪些旧规则已被新的反例或脚本工具替代？
□ 哪些工具脚本已不再被调用（孤儿脚本）？
□ 哪些 Reference 已失去入口？
□ 哪些规则只是当时为了修一次性偶发 bug 临时加的“以防万一”限制？
□ 本次实际删除或归档了什么？
```

**如果本次升级只有增加、没有删除，必须给出充分理由**。好系统的精悍不是因为功能少，而是因为无用代码和过期规则被持续清理。

---

## 5. 轻量反馈机制（保护用户心流）

日常运行时绝不主动打扰用户。**只有当以下信号出现时，才向用户提问**：
1. 同一个致命问题连续复现 2 次以上；
2. 用户主动表达了强烈的偏好或不满；
3. 发现了一个重大的新场景需要新增独立工具。

提问时直奔主题：
```text
本次运行发现了一个可复用的优化点：
- [具体现象与建议的工具下沉/反例补充方案]
是否确认将其固化进该 Skill？
```
