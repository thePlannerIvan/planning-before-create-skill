# 管控、脚本与 Contract

把 Workflow Map 转成 Skill 系统时，使用本文件选择足以防住失败的最弱管控。

## 先区分两种复杂度

- **语义不确定性**：任务是否依赖理解、比较、抽象、创意、取舍或表达。
- **机械脆弱性**：搜索、格式、顺序、保存、恢复、校验或发布是否容易出错。

| 任务 | 优先设计 |
|---|---|
| 高语义不确定、低机械脆弱 | 完整 Prompt + 判断框架 |
| 高语义不确定、高机械脆弱 | 模型判断 + 脚本管理状态与机械动作 |
| 低语义不确定、高机械脆弱 | 脚本直接完成 |
| 低语义不确定、低机械脆弱 | 简单 Prompt |

流程长不代表应该让脚本控制语义。脚本可以控制阶段顺序，但必须把当前 Stage 的完整任务交给模型。

## 管控工具

| 工具 | 适用场景 | 不应承担 |
|---|---|---|
| Prompt / Stage | 语义理解、判断、创意和表达 | 机械搜索、格式转换、状态保存 |
| 工作文件 | 跨阶段记忆、回到来源、恢复 | 记录所有临时思考 |
| Script / Hook | 搜索、转换、保存、恢复、校验、打开页面 | 替代开放语义判断 |
| Dispatcher | 当前阶段、前置条件、回执、恢复 | 把模型淹没在内部协议中 |
| Contract | 真正的机器交接和版本绑定 | 给每个非平凡步骤填表 |
| Human Checkpoint | 模型无法替代的方向、承诺、风险与知识 | 审阅模型能够自行完成的机械分类 |

## 脚本价值测试

加入脚本前逐项检查：

```text
□ 动作是否重复且确定？
□ 人工或模型重复执行是否容易出错？
□ 脚本是否明显减少上下文或操作负担？
□ 输出是否由真实下游消费？
□ 失败是否能返回可诊断原因？
□ 是否只是把一句 Prompt 变成额外命令、文件和回执？
```

最后一项为“是”而前五项没有明确收益时，不应加入脚本。

## Contract 决策测试

只有至少一个条件成立时才使用 Contract：

- 下游脚本必须解析；
- 多个执行者或会话需要可靠交接；
- 任务需要中断恢复；
- 错误字段会触发高成本或不可逆操作；
- 人工决定必须绑定特定内容版本；
- 产物需要确定性安装、发布或外部集成。

普通语义步骤可以用自然语言产物、Markdown、工作记忆或用户确认衔接。

## Contract 最小化

Contract 只保留下游实际消费的字段。设计时标明：

```text
Contract：
- 消费者：
- 消费时机：
- 缺失会造成什么失败：
- 最小字段：
- Producer：
- Consumer：
- Validator 能证明什么：
- Validator 不能证明什么：
```

若说不出消费者和具体失败，不建立 Contract。

## Dispatcher 边界

Dispatcher 可以负责：

- 当前阶段和路线；
- 前置文件是否存在；
- 调用确定性 Validator；
- 保存、恢复和错误诊断；
- 启动审阅页面；
- 返回当前完整 Stage。

Dispatcher 不负责：

- 把开放任务拆成大量字段；
- 决定语义质量；
- 要求模型重复报告脚本已经知道的状态；
- 让模型读取内部状态协议才能理解当前任务。

## 资源放置

| 内容 | 位置 |
|---|---|
| 所有路径都需要的全景和路由 | `SKILL.md` |
| 当前阶段完整任务 | `stages/`或直接由 `SKILL.md`指向的单层文件 |
| 非显然领域知识 | `references/` |
| 确定性机械动作 | `scripts/` |
| 真正机器接口 | `contracts/` |
| 输出使用的模板与素材 | `assets/` |

不要把同一 Stage 拆成“只有文件引用的 Stage”和另一份同时必须读取的 Instruction。模型在进入阶段时应一次得到完整任务。
