# Stage 与上下文设计

把已确认的 Workflow Map 转成可由另一位模型执行的 Stage 时，完整读取本文件。

## 核心原则

目标 Skill 先提供整个任务的简明全景；每次运行再披露当前 Stage 的完整任务。渐进披露意味着“在正确时间完整说明”，不是把当前任务压缩成文件索引。

一个 Stage 围绕一个主要结果或一项连贯决定组织。阅读、比较、抽象、选择等动作如果共同服务于同一结果，不要人为拆散；只有目标、输入或完成边界明显不同时才拆 Stage。

## 完整 Stage 结构

```markdown
# [Stage 名称]

## 这一步在做什么
[目的，以及它在整体流程中的位置。]

## 为什么需要这一步
[它防住什么失败，为下游解决什么问题。]

## 输入及其作用
- [输入 A]：[在本阶段用来判断什么]
- [输入 B]：[在本阶段用来约束什么]

## 主要结果与认知动作
[本阶段要完成什么结果；哪些紧密相关的理解或判断共同服务该结果。]

## 判断框架
- [应该观察的维度]
- [好结果的特征]
- [容易误判的反例]

## 不要做什么
- [不属于本阶段的下游任务]
- [常见抢跑或伪完成]

## 工作方式
[模型如何推进、何时回到资料、脚本只负责什么。]

## 人机介入
[只有哪些模型无法替代的决定需要找人；没有则明确写无。]

## 产物
[对话确认、Markdown、工作记忆、机器接口或其他必要产物。]

## 完成标准
- 语义完成：[模型真正做到什么]
- 机器检查：[可以确定性检查什么]
- 不能由 Validator 证明：[需要样例或人判断什么]
```

## 判断框架，不是伪确定规则

开放语义任务优先提供：

- 观察维度；
- 区分好坏的依据；
- 边界案例；
- 反例和常见误判；
- 回到原始材料的方法；
- 结果对下游的实际用途。

只有当阈值、枚举或字段在现实中确实存在，并且下游机器需要消费时，才把它们设为硬规则。不要用固定字数、固定条数或复杂 Schema 伪装对质量的理解。

## 产物与持久状态

只有这些状态需要落盘：

- 跨阶段或跨会话仍需使用；
- 下游机器需要解析；
- 需要从摘要回到原始来源；
- 需要中断恢复或多人交接；
- 需要绑定当前版本的人工反馈；
- 错误丢失会造成明显返工或风险。

自然共创、低风险临时判断、不会被下游消费的过程，不强制结构化。重要不等于必须文件化。

## 检查清单

```text
□ 模型是否先看到整个 Skill 的目的和方法？
□ 当前 Stage 是否无需追读多份文件才能理解任务？
□ 输入是否说明了作用，而不只是路径？
□ 是否围绕一个主要结果，且没有人为拆散相关认知动作？
□ 是否给了判断框架，而不是伪精确限制？
□ 是否写清不做什么和语义完成标准？
□ 产物是否真的需要持久化？
□ Validator 是否只声称验证它能够证明的部分？
```
