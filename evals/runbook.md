# evals 跑法

`evals.json` 里每条是一条**语义验收用例**：给它一个真实 Prompt，看它是否走到正确的路线、
是否做了该做的事、有没有做不该做的事。里程碑 4 第 2 步跑的就是这里。

`route_expected` 是确定性可校验的（`patch` / `lean` / `system`），`must_do` 与
`must_not_do` 是行为观察项。所以每条 eval 的结论只有三种：**过 / 不过 / 有争议**。

## 怎么跑一条

1. **起一个干净上下文的 agent**（新会话或子代理），**不要预热**——它不该事先知道答案。
2. 把 `prompt` 字段**逐字**发给它，不要加任何提示（不要说「这是一个 Skill 规划任务」，
   那等于告诉了它路线）。
3. 让它跑完，收集它的产出。
4. 按下表判：

```text
□ route_expected：它选的路线与字段一致吗？
    （Patch = 只改局部不重设计 / Lean = 最小实现不跑满里程碑 / System = 走四个里程碑）
□ must_do：逐条确认真的做了，不是嘴上提了一句。
□ must_not_do：逐条确认没做。**触犯任意一条即不通过**，没有「轻微触犯」。
□ 对 System 用例额外看：它有没有在实现前把 OKR 蓝图、概念锚点与工具边界摆给用户确认
    （原则 6：不替用户做价值判断，也不把人变成审批机）。
```

## 什么时候跑

- **改动本 Skill 之后**：至少跑与本次改动相关的那一条。改了路线判据 → 跑三条路线各一条
  （`patch-description` / `lean-simple-skill` / `system-brand-analysis`）。
- **发布前**：至少跑 `system-subtractive-upgrade` —— 它验的是减法审计，而减法审计是
  这个 Skill 最容易被跳过的一步。

## 判据写在哪

用例本身的 `must_do` / `must_not_do` 就是判据，**不要另建一份**。改判据就改 `evals.json`，
保持单一真相源；跑法（流程）留在这个文件里。

## 减法审计的连带项

退役某个概念、规则或文件时，**同一次改动里**把它在 `evals.json` 里的表述一起清掉。
留着一套用废词的 eval，跑它等于把模型推回旧架构——这比不跑更坏。
